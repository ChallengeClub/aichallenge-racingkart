# End-to-End AI部門の安定周回ベースライン

## 1. この文書の目的

この文書は、End-to-End AI部門でまず安定して周回し、提出可能なソースを作るために、何を試し、どの構成に到達したかをまとめたものです。

速さを最初から追うのではなく、次の順序を重視します。

1. 大会と同じセンサ条件で発進できる
2. コースを1周できる
3. 同じ設定で連続周回できる
4. その後に速度とタイムを上げる

## 2. dev更新後に分かったこと

2026年8月時点の`dev`には、End-to-End向けの`make e2e`が追加されています。このモードはカメラとLiDARを有効にし、IMU、GNSS、V2Xを無効にします。開始位置はランダムで、NPCは2台です。

以前の`make dev`による評価は、現在の`dev`ではカメラとLiDARが無効になるため、最新の公式E2E条件の評価としては扱えません。今回から次を使い分けます。

- `make e2e`: NPCを含む公式E2E練習条件
- `make simulator-e2e-no-npc autoware-simulator`: センサとランダム開始は同じで、NPCだけを除いた原因切り分け用条件

NPCなしモードは大会結果そのものではありません。自車の周回番号と区間番号を混線なく測るための診断用です。

## 3. PilotNetだけでは安定しなかった理由

SW部門のMPC走行から6,763枚を抽出し、PilotNetを操舵専用として再学習しました。検証データ上では操舵角の相関が高く、平均誤差も小さい結果でした。

しかしシミュレータでは、セクション3または5で壁へ近づき、停止しました。これは「教師データ上の画像を見て正しい操舵を予測すること」と、「自分の小さな誤差が積み重なった状態からコースへ戻ること」が別問題だからです。

教師のMPCはおおむね理想的な走行ラインを通ります。そのため、PilotNetは次の画像を十分に学習していません。

- コース端へ寄った画像
- 車体が壁を向いた画像
- 操舵を大きく戻す必要がある画像
- ランダム開始直後の画像

この問題は、今後DAggerや人間の修正操作を追加収集して改善します。今回の提出ベースラインでは、PilotNetを無理に主制御へせず、まず実走で安定性を示したLiDAR学習モデルを採用しました。

## 4. 今回の提出ベースライン

構成は次の3要素です。

### 4.1 TinyLiDARNetによる操舵

LiDARの距離列をニューラルネットワークへ入力し、操舵角を出します。既存モデルは未補正でもセクション5まで進み、PilotNetより良いオンライン走行性能を示しました。

### 4.2 車輪速による速度制御

元の固定加速度`0.6`では5 m/sを超え、旋回時に衝突しました。一方、固定加速度を`0.25`や`0.4`へ下げるだけでは、静止摩擦を越えられず発進できませんでした。

そこで、許可されている車輪速を使う比例制御へ変更しました。

```text
加速度 = 比例ゲイン × (目標速度 - 現在速度)
```

発進時は最大`0.6`を出し、目標速度へ近づくほど加速度を弱めます。目標を超えた場合は最大`-0.2`で減速します。現在の目標速度は`2.5 m/s`で、平坦部の実速はおおむね`1.9〜2.0 m/s`でした。

### 4.3 障害物接近時だけ働くLiDAR安全残差

学習モデルの操舵を通常時の主役にし、正面4 m以内が塞がったときだけ補正します。

1. 正面の20パーセンタイル距離を調べる
2. 左右20〜80度の空き距離を比べる
3. 空いている側へ操舵を加える
4. 速度目標を一時的に下げる
5. 旋回を始めた直後に補正が消えないよう、6スキャンだけ方向を保持する

この補正は地図、自己位置、IMU、GNSSを使いません。TinyLiDARNetと同じLiDAR、および速度制御用の車輪速だけで完結します。

## 5. 調整過程と結果

| 構成 | 条件 | 結果 |
|---|---|---|
| 再学習PilotNet + 速度制御 | NPCなし | セクション3で停止 |
| PilotNet + 初期安全補正 | NPCなし | セクション5まで改善後、停止 |
| TinyLiDARNet、固定加速度0.6 | NPCありE2E | 約5 m/s、セクション5付近で停止 |
| TinyLiDARNet、固定加速度0.25/0.4 | NPCありE2E | 発進できず |
| TinyLiDARNet + 速度制御 | NPCありE2E | セクション5で停止 |
| 上記 + 強い安全残差 | NPCありE2E | セクション7まで進むが過介入 |
| 上記 + 限定安全残差 | NPCありE2E | 500秒無停止、最大lap 3 / section 8、終了時も走行中 |
| 上記 + 限定安全残差 | NPCなし診断 | 500秒無停止、連続2周完走、3周目を走行中 |
| 提出tarから構築した評価イメージ | NPCありE2E | 300秒無停止、最大lap 2 / section 8、終了時も走行中 |

NPCなし診断の詳細値は次のとおりです。

- 1周完了: 監視開始から約209秒
- 2周完了: 約410秒
- 平均速度: 約1.84 m/s
- 最大速度: 約2.41 m/s
- 500秒終了時: lap 3、section 5、走行中

NPCありでは`/awsim/status`のlapとsectionが複数車両分と思われる値の間で揺れるため、個々の表示値を自車の厳密なラップタイムとはみなしません。ただし、500秒間停止せず、lap 3とsection 8までの値を観測し、終了時にも約1.7 m/sで走行していました。

さらに、`create_submit_file.bash`で作った約3.8 MBの提出tarから評価用Dockerイメージを新規構築しました。25パッケージのビルドが成功し、そのイメージだけで300秒走行しました。最大lap 2 / section 8を観測し、終了時も約1.76 m/sで走行していたため、開発環境のマウントに偶然依存していないことも確認できました。

## 6. 提出時の設定

`reference.launch.xml`の既定制御を`tiny_lidar_net`に変更しました。主な設定は次にあります。

- `tiny_lidar_net_controller/config/tiny_lidar_net_node.param.yaml`
- `tiny_lidar_net_controller/tiny_lidar_net_controller_node.py`
- `pilot_net_controller/lidar_safety.py`

安全残差の共通実装をPilotNet側にも接続しているため、今後PilotNetを再度主制御に戻す際も同じ考え方を利用できます。

## 7. 次の改善順序

まず今回の低速ベースラインを提出形式で再確認します。その後は次の順が現実的です。

1. ランダム開始を変えた公式E2E試験を複数回行う
2. NPCとの接触・追従・回避を個別に記録する
3. PilotNetが失敗した場面を人間または安全制御で修正し、DAgger用教師データとして追加する
4. PilotNetへ速度、過去画像、LiDARの特徴量を追加し、時間的な状況を判断できるようにする
5. 安定性を保ったまま目標速度を少しずつ上げる
6. 十分な安定ベースラインができた後、SACには小さな操舵・速度補正だけを学習させる

SACを後段に置く理由は、完走できない方策へタイム報酬を与えても学習が不安定になりやすいためです。まず完走可能な方策を作り、その周囲の小さな改善問題へ変えることが重要です。

## 8. 現時点の結論

今回の構成は、少なくともNPCなしの同一センサ条件で連続2周、NPCあり公式E2E条件で500秒の無停止走行を確認できました。したがって「まず安定的に周回できる提出ソース」という第一段階の候補として扱えます。

一方、ランダム開始やNPC配置を変えた複数回の再現試験は必要です。提出tarを使ったビルドと300秒の実行確認までは完了しました。タイム改善用のPilotNet + SACは、このベースラインを壊さずに段階的に置き換えていく方針とします。

このベースラインを保った最初の速度改善は、[04_Stable_Time_Improvement.md](04_Stable_Time_Improvement.md)にまとめています。
